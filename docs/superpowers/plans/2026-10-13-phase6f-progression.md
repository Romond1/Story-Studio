# Phase 6F progression implementation plan

Start implementation only after the Phase 6E acceptance gate passes. Preserve the dedicated branch and all uncommitted work. Use synthetic identities and disposable application profiles for writes.

Reuse application-level roster IDs as permanent student identities. The private progression repository lives in userData, outside lesson folders. It owns accepted event receipts, captured run context, completion/history records, pending reward requests, teacher decisions, inventory, relic progress and episode completion. Phase 7 will extend this same service with classes and profile views; it must not introduce another student database.

Use a serialized transaction queue and atomic replacement of one versioned JSON document. Apply an event and its durable idempotency receipt in the same write. An identical replay returns the saved result; the same event identity with changed content is rejected. Failed writes leave memory and disk at the previous revision. Reject corrupt existing stores rather than silently starting empty or overwriting them. Bound input collections and numeric quantities; validate records read from disk as well as IPC input.

Capture module type, episode/adventure identity, participants, and immutable adventure definitions when a run begins through authenticated Control. Main must verify reported module events against the active transport context or a Core-registered Activation run. Accept module results only from the running lifecycle. Teacher approval is an authenticated Control operation and is separate from a module's reward request. Modules never receive private profile records or a write API.

Use existing module events for completion, scores and reward requests. Scores are recorded as temporary session results and are not inferred assessments or automatic achievements. Resolve reward IDs against explicit adventure definitions; never match names. Where existing module reward keys differ, provide an explicit authored association or teacher selection before approval. Unknown requests remain visible with an actionable reason and cannot mint undefined rewards. Captured guest participants may take part in a run but never receive permanent grants. Changing the current selected student cannot reassign an earlier result.

Add a compact Control progression panel in Challenge/Mastery and Teach: captured results, pending requests, approve/reject, current adventure inventory, explicit manual reward adjustments, relic advancement and episode completion. Every mutation has a command ID and durable receipt. Changes to reward/relic definitions do not delete historical receipts. Adventure scopes isolate inventory and relic IDs even when display names match.

Provide an explicit legacy mapping procedure using stable source identifiers and chosen existing roster IDs; do not migrate by display name or automatically import legacy scores/relics. Preserve legacy settings and lesson data. Plan Phase 7 profile editing as an extension of the existing roster storage rather than migrating identities implicitly.

Tests: lost acknowledgment and replay after restart; payload collision; concurrent approval; failed atomic write; corrupt store; unknown/archived students; guests; stale run; mismatched participants; unauthorized renderer; reward definition mismatch; same student across two adventures; manual relic progress; package privacy. Native acceptance: two isolated students complete an actual Challenge, request/approve one reward, inspect it in Mastery, replay and restart with exactly one grant, export and inspect privacy. Only then continue to 6G.
